# 系统设计调整工作流

OOC 系统多次大型重构，最大的风险是**涨潮不退潮**——新设计涌入、旧设计/文档/代码不清理，熵增失控。这条工作流是退潮闸门：每次系统设计调整都留痕、被多视角 review、强制一致性回流、并在落地后独立验收。

工作流有两道 review 闸门，问的是不同的问题：步骤 2 的**设计 review**问「改动对不对」，步骤 4 的**落地验收**问「改动有没有照约定落到位」。前者把关方向，后者把关执行——`landed` 只是 Supervisor 落地后的自我断言，必须经一道独立核对才算真的退潮完成。

## 何时走这条流程

**任何系统设计调整**：维度核心设计的增删改、对象模型变更、跨维度/内置对象交叉契约的调整、builtin 家族设计变更、退役某个符号/概念。

不走这条流程：纯实现 bug 修复（不动设计契约）、测试增补、文档错别字。判据是**「这次改动是否触动某个设计元素的契约」**——触动就走。

## 设计元素注册表 = `index.md` 的 `##` 元素清单

[`./index.md`](./index.md) 是 OOC 全部核心设计的设计层总览，它 A–E 区的每个 `##` 元素（顶层 / 各维度 / builtins / 各交叉对）就是一个**设计元素**。本工作流的 review fan-out 据此清单判定「本次改动受影响哪些元素」。index.md 因此是双重身份：既是设计总览，也是 review 的元素注册表。

## 四步流程

### 步骤 1 · 发起 issue

在 [`../../docs/issues/`](../../docs/issues/) 新建 `YYYY-MM-DD-<slug>.md`，按模板（见该目录 `README.md`）写清：

- **背景 / 动机**：为什么要改。
- **现状**：当前设计怎么说的（锚 index.md / 对应 self.md）。
- **改动提案**：要改成什么。
- **受影响设计元素**：对照 index.md 的 `##` 元素清单，逐一列出本次改动触及的元素（这份清单驱动步骤 2 的 fan-out）。
- **风险与权衡**：可能引入的矛盾、跨维度连锁。
- **待裁决点**：需要 Supervisor 拍板的分叉。

### 步骤 2 · review fan-out

**先过前提闸门，再 fan-out**（本工作流最易漏的一步——fan-out 擅长审「怎么做对」、不擅长审「该不该做」，所以「该不该做」必须前置）：

- **先证伪、再 validate**：把改动方向最强的单点失败假设写成一句话，用最省的方式（一条 grep、读一段码）去打它；打穿了就别 fan-out——方向本身不成立，省下整场 review。
- **编排重量按改动的不可逆性、不按话题的宏大感**：删 / 退役 / 可逆 / grep 可验回归 → 轻流程（一条 grep + 一次 self-review 就够，不必 fan-out）；加机制 / 动核心 loop / 不可逆 → 才配 fan-out。**fan-out 是给「要新增什么」的，不是给「要删什么」的。**

过了闸门，并发派 sub agent：

- **每个受影响设计元素各派一个 reviewer**：以「我是这个设计元素的主人」的视角，审本次改动对该元素的契约影响——是否矛盾、是否连带需改、是否有更好的做法，补具体评论。**尤其问一句接口边界**：这次改动是不是把某一个对象的实现细节/做法，当成了协议层的普遍约定、强加给了所有对象？协议该管的（统一入口/寻址）和实现该自由的（各对象自己的设计与关注点）分清了吗？——守高内聚低耦合 + 接口原则：协议画好分界、给实现留自由。
- **外加一个完整性批评官**：扫 index.md 全清单 + 对应 self.md，专问「**还漏了哪个未被 issue 列为受影响、但其实会被波及的元素？**」以及内部自洽 / 与 source 一致 / 术语漂移 / 设计-实施越界。

派单约束：reviewer **不自己 commit、不直接改文件**，只把评论回给 Supervisor 汇总；涉及运行时验证的 session 用 `_test_<agent>_<timestamp>` 前缀并在验证后清理。

### 步骤 3 · 汇总裁决与一致性回流

Supervisor：

1. 汇总各 reviewer + 完整性批评官的意见，记进 issue 的「review 记录」段。
2. 裁决跨维度冲突与待决点，更新改动方案。
3. 落地：改对应 self.md（面向实施）/ index.md（面向设计）/ 代码（**涉及源代码变更走 worktree 隔离，见下节**）。
4. **一致性回流（强制）**：index.md 与各 self.md 是同一设计的两个投影，落地后必须同步——改了 self.md 核心契约就同步 index.md 对应节，反之亦然。退役某符号/概念时，全树（index.md + 各 self.md + builtin md）引用一并清理（退潮）。
5. issue 标记 `decided`（方案已拍板）→ `landed`（改动已应用，进入步骤 4 验收）。

### 步骤 4 · 落地验收 review

`landed` 是 Supervisor 落地后**自我断言**的状态——动手的人和宣布完成的人是同一个，缺独立核对。本步骤把「落地」交给一轮验收 review：对照 issue 核**实际落地的文档/代码是否如提案完成改造**。注意这不是重审设计对不对（那是步骤 2），只问改动有没有照约定落到位。

并发派 sub agent 做验收（改动大时可按受影响元素各派一个验收 reviewer，默认一个验收官对照 issue 清单逐条核）：

- **文档验收**：issue「改动提案」+「受影响设计元素」逐条核——对应 self.md / index.md 是否真改了、成对回流是否完整（一个投影改了另一个漏没漏）。
- **代码验收**：若涉及源码，issue 决定的实现是否真在代码里（锚点存在、行为符合）、测试 / 质量门是否绿（`bun run verify` 等）。
- **退潮验收**：issue 若退役了符号 / 概念，全树（index.md + 各 self.md + builtin md + 源码）引用是否清干净——接 `check:doc-drift`、`check-no-deprecated-symbols`。
- **漂移验收**：落地过程是否引入了 issue 未提及的新偏差。

验收 reviewer 同样**不自己补、不直接改文件**，只把缺口回给 Supervisor。Supervisor 据反馈补落地（issue 维持 `landed` 继续补），直到验收无缺口——issue 标记 `verified`，闭环完成。验收发现的实质设计问题（而非落地遗漏）按新一轮系统设计调整另起 issue，不在本轮夹带。

## 涉及源代码变更的 issue：worktree 隔离开发

issue 的落地若**涉及源代码变更**（`packages/@ooc/` 等实现代码，区别于纯对象树文档调整），不在主工作区直接改，而是**为该 issue 新建一个 git worktree 分支**隔离开发：

- worktree 落在源码仓库根的 **`.worktree/` 目录**下，每个 issue 一个（分支 / 目录名关联 issue slug，如 `.worktree/<slug>/`）。
- 在该 worktree 分支上完成实现 + 自验证，与主工作区、与其它 issue 的 worktree 互不污染——多 issue 可并行各自隔离。
- 开发完按常规合入，issue 的「裁决」段记录对应 worktree 分支。

纯设计文档调整（只改 index.md / self.md / builtin md，无源码改动）不需要 worktree。

## 一致性的根

index.md **面向设计**（核心契约 + 交叉）、各 self.md **面向实施**（本维度核心 + 源码锚点），侧重不同、不是双份副本。保证二者不漂移的，正是这条工作流的步骤 3.4——**任何设计调整都成对回流**；步骤 4 的落地验收再独立兜底，专抓「回流漏了一边」「退役没清干净」「代码与设计对不上」这些落地遗漏。脱离工作流的零散改动是漂移之源。
